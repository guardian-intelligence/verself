<sdk_boundary>
- SDK packages are downstream facade layers for customers, operators, CLI commands, browser server routes, docs examples, and future Terraform/provider-style integrations. Product services must not import `src/sdks/*` packages.
- Service-owned generated Go clients under `src/services/*/client` are transport clients for repo-owned service-to-service calls. Their consumers should be product services and service-adjacent runtime code, not curated SDK packages.
- SDK generation starts from canonical Smithy contracts under `src/contracts` and emits SDK-owned code under `src/sdks/<language>/...` or the frontend SDK package. OpenAPI inputs are transitional/generated compatibility projections, not the contract authority. Repo-owned service clients are generated separately from internal projections under `src/services/*/client`. Do not move service generated clients into SDK packages, and do not make SDK packages import service generated Go clients as their implementation detail.
- Handwritten SDK code owns facade ergonomics: customer/operator auth selection, bearer-token handling, retry policy, idempotency key policy, pagination helpers, waiters, error normalization, tracing headers, and DTO conversion. Generated SDK resource cores should own repetitive operation bindings derived from the canonical contract model.
- SDKs must not implement SPIFFE or mTLS as an auth mode. Service-to-service SPIFFE calls use service generated transport clients directly with caller-provided mTLS `http.Client` values. Browser server routes, the `verself` CLI, customer automation, and docs examples should use curated SDKs.
</sdk_boundary>
