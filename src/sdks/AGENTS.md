<sdk_boundary>
- SDK packages are downstream facade layers for customers, operators, CLI commands, browser server routes, docs examples, and future Terraform/provider-style integrations. Product services must not import `src/sdks/*` packages.
- Service-local Go clients/adapters under `src/services/*/client` or `src/services/*/internalclient` are repo-owned integration code. Their consumers should be product services and service-adjacent runtime code, not curated SDK packages.
- SDK implementations start from canonical Smithy contracts under `src/smithy`. OpenAPI inputs are generated compatibility projections, not the contract authority. Repo-owned service clients live separately under `src/services/*`. Do not move service clients into SDK packages, and do not make SDK packages import service-local Go clients as their implementation detail.
- Handwritten SDK code owns facade ergonomics: customer/operator auth selection, bearer-token handling, retry policy, idempotency key policy, pagination helpers, waiters, error normalization, tracing headers, and DTO conversion. SDK transport implementations may be handwritten or generated from public OpenAPI projections where tooling is reliable.
- SDKs must not implement SPIFFE or mTLS as an auth mode. Service-to-service SPIFFE calls use service-local typed clients/adapters with caller-provided mTLS `http.Client` values. Browser server routes, the `verself` CLI, customer automation, and docs examples should use curated SDKs.
- Generated SDK transports and validators are cached projections, not semantic truth. Any source import under `__generated` must correspond to a current generator owner in the build graph. When replacing a generator with hand-written or OpenAPI-backed code, remove the generated import and restore the new generator input in the same change; do not rely on an ignored stale file in a golden workspace. See `docs/architecture/generated-artifact-governance.md`.
</sdk_boundary>
